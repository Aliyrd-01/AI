# Multi-Agent Shared Context — Как объединить агентов в единую систему

## Проблема

Есть несколько AI-агентов (Big Pickle, Mistral, Gemini и т.д.), каждый работает автономно.
Один пишет код, другой анализирует, третий тестирует. Но они не видят друг друга:
- Big Pickle не знает что Mistral вчера нашёл баг
- Gemini не знает что Big-Pickle сегодня изменил архитектуру
- Каждый работает в своём контексте, как три программиста в разных комнатах без связи

## Решение — общий контекст

### Что это

Один источник правды (файл или БД), который:
1. **Читают** все агенты перед началом работы
2. **Пишут** все агенты после завершения работы

### Из чего состоит общий контекст

**1. Описание проекта** (пишется один раз, читают все):
- Что за проект, какую проблему решает
- Какая архитектура (монолит, микросервисы, etc.)
- Какой стек (Python, FastAPI, PostgreSQL, etc.)
- Где лежат ключевые файлы

**2. Журнал действий** (пишут все агенты):
- Кто: "я Big-Pickle, я написал эндпоинт /api/users"
- Кто: "я Mistral, я нашёл баг в handle_login()"
- Кто: "я Gemini, я написал тесты для /api/users"
- Каждая запись = агент + действие + время

**3. Текущие задачи** (как Kanban-доска):
- todo — ещё никто не взял
- in progress — агент взял и делает
- done — выполнено

**4. Известные проблемы**:
- Баги, которые нашли агенты
- Архитектурные ограничения
- Технический долг

## Как это работает

### Шаг 1: Агент берёт задачу
- Читает общий контекст
- Видит что проект делает, что другие агенты уже сделали
- Берёт задачу из todo, помечает in progress

### Шаг 2: Агент выполняет
- Работает над задачей
- Учитывает контекст: не ломает то что сделали другие, не дублирует работу

### Шаг 3: Агент завершает
- Записывает в журнал: "я сделал X, изменил файл Y"
- Помечает задачу done
- Если нашёл баг — записывает в "известные проблемы"

### Шаг 4: Следующий агент
- Читает общий контекст
- Видит: "Big-Pickle написал эндпоинт, Mistral нашёл баг в нём"
- Берёт задачу "исправить баг"

## Архитектура

```
                    ┌─────────────────────┐
                    │   Оркестратор       │
                    │   (кто раздаёт      │
                    │    задачи)          │
                    └─────────┬───────────┘
                              │
                    ┌─────────▼───────────┐
                    │   Общий контекст    │
                    │   (файл/БД)         │
                    │                      │
                    │  - Описание проекта  │
                    │  - Журнал действий   │
                    │  - Текущие задачи    │
                    │  - Известные баги    │
                    └────┬────┬────┬──────┘
                         │    │    │
              ┌──────────┘    │    └──────────┐
              ▼               ▼               ▼
        ┌──────────┐   ┌──────────┐   ┌──────────┐
        │ Agent 1  │   │ Agent 2  │   │ Agent 3  │
        │ (код)    │   │ (анализ) │   │ (тесты)  │
        └──────────┘   └──────────┘   └──────────┘
```

## Кто такой оркестратор

Это агент (или скрипт), который:
- Принимает задачу от пользователя
- Разбивает её на подзадачи
- Определяет какому агенту какая подзадача
- Следит за выполнением
- Собирает результат

Может быть:
- Отдельный AI-агент (Big-Pickle как головной)
- Простой скрипт на Python
- n8n workflow
- Любой другой процесс

## Варианты реализации

### Вариант 1: JSON-файл (простой)
- Один CONTEXT.json на диске
- Все агенты читают/пишут этот файл
- Плюс: нет зависимостей, просто
- Минус: race condition если два агента пишут одновременно

### Вариант 2: SQLite (надёжный)
- БД в одном файле
- ACID — нет конфликтов при параллельном доступе
- Плюс: надёжно, можно запросы делать
- Минус: чуть сложнее чем JSON

### Вариант 3: Через n8n (оркестрация)
- n8n как центральный хаб
- Агенты — webhook-ноды в n8n
- Контекст — в БД n8n (Postgres)
- Плюс: визуальный мониторинг, логи
- Минус: привязка к n8n

### Вариант 4: A2A Protocol (стандарт)
- Google Agent-to-Agent протокол
- Каждый агент — HTTP-сервер с Agent Card
- Стандартный способ общения между агентами
- Плюс: стандарт, масштабируемость
- Минус: пока мало готовых решений

## Сравнение

| | JSON-файл | SQLite | n8n | A2A |
|---|---|---|---|---|
| Простота | Очень просто | Средне | Средне | Сложно |
| Надёжность | Низкая | Высокая | Высокая | Высокая |
| Зависимости | Нет | Нет | Да | Да |
| Мониторинг | Нет | Вручную | Да | Вручную |
| Масштабируемость | Плохая | Хорошая | Хорошая | Отличная |

## Рекомендация

Для начала — **JSON-файл** или **SQLite**. Не нужно строить инфраструктуру.
Один файл, который все агенты читают и пишут. Потом, если масштаб будет расти —
переходи на n8n или A2A.

Главное — не сам инструмент, а **процесс**:
1. Агент читает контекст перед работой
2. Агент записывает что сделал после работы
3. Оркестратор следит чтобы не было конфликтов

## Ключевой принцип

**Все агенты должны знать:**
- Что проект делает (описание)
- Что другие агенты уже сделали (журнал)
- Что нужно сделать (задачи)
- Что не работает (баги)

**Если хотя бы один агент этого не знает — он работает вслепую и ломает чужую работу.**
